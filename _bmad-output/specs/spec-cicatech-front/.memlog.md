- (capability) CAP-1. Intent: gérer les comptes utilisateurs (créer, lister, voir le détail, modifier, activer/désactiver, réinitialiser le mot de passe, changement de mot de passe par l'utilisateur). Success: un administrateur peut réaliser tout le cycle de vie d'un compte depuis l'écran Gestion des utilisateurs, avec messages de succès/erreur et validations de formulaire.
- (capability) CAP-2. Intent: gérer les groupes d'utilisateurs (créer, lister, détail, modifier, activer/désactiver, gérer les membres). Success: un groupe peut être créé, ses membres ajoutés/retirés, et son statut basculé, avec unicité du nom vérifiée à la création et à la modification.
- (capability) CAP-3. Intent: gérer les habilitations (rôles sur utilisateur/groupe, association/retrait). Success: un rôle porte une liste de permissions et peut être associé à des utilisateurs/groupes ; permissionGuard bloque l'accès aux routes non autorisées.
- (capability) CAP-4. Intent: gérer les notifications e-mail liées aux comptes (activation/désactivation par type d'événement, journal d'envoi). Success: un administrateur active/désactive une notification par type, et chaque envoi simulé est journalisé et consultable.
- (capability) CAP-5. Intent: gérer les agents RH (créer, lister, détail, modifier, activer/désactiver). Success: un agent est géré indépendamment de son affectation, avec les mêmes garanties d'unicité et de validation que les autres entités.
- (capability) CAP-6. Intent: gérer les structures organisationnelles avec hiérarchie (créer, lister, détail, modifier, activer/désactiver, rattacher à un parent). Success: une structure a au plus un parent, aucune auto-référence ni cycle n'est permis, et une structure inactive ne peut plus recevoir de nouveaux rattachements.
- (capability) CAP-7. Intent: affecter un agent à une structure active et rattacher une structure à une structure parente active. Success: écran Affectations & rattachements applique les règles de CAP-6 et affiche les erreurs renvoyées par le service en cas de violation.
- (capability) CAP-8. Intent: générer automatiquement l'organigramme à partir des agents et structures existants, sans jamais être saisi manuellement. Success: l'organigramme reflète toujours en temps réel l'état courant des structures/agents (recalcul réactif via signals).
- (capability) CAP-9. Intent: préparer la bascule mock -> API backend réelle sans réécrire composants ni parcours fonctionnels. Success: remplacer une implémentation MockXRepository par HttpXRepository + sa registration DI dans app.config.ts suffit à brancher le vrai backend pour une entité donnée (gouverné par le spine architecture AD-1 à AD-5).
- (constraint) Sidebar Paramétrage & Sécurités limité à exactement 4 entrées : Gestion des utilisateurs, Groupes d'utilisateurs, Habilitations, Notifications e-mail. Les opérations CRUD/activation/détail restent dans les écrans, jamais en sous-menus.
- (constraint) Les composants ne doivent jamais accéder aux données mockées directement -- uniquement via le Service, lui-même via le Repository injecté (cf. spine AD-2).
- (constraint) Aucune structure inactive ne peut être choisie comme parent ou comme affectation pour un nouvel agent (règle métier RH, valable pour toute nouvelle association).
- (constraint) Le remplacement du backend mock par une vraie API se fait uniquement au niveau Repository + configuration DI (app.config.ts), sans réécrire Services, Components ni Models (cf. spine AD-3).
- (constraint) Chaque entité garde un contrat Repository/Service spécifique et minimal (pas de IRepository<T> générique forcé), pour respecter Interface Segregation et permettre la substitution Mock/Http sans changement côté Service (Liskov) -- cf. spine AD-5.
- (non-goal) Pas de logique de refetch/synchronisation/cache HTTP développée pendant la phase mock -- différée à l'intégration API réelle (cf. spine AD-1, Deferred).
